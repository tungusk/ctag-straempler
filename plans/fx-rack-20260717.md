# FX rack — slot-based, centralized effects (design, 2026-07-17)

Status: **DESIGN / not started.** Arlo-initiated after the FX float-through +
soft-clip fix (commit e6cf6ba). Goal: replace the fixed 5-effect chain + the
triplicated 23-line FX menu with a centralized slot rack that machines
instantiate with as many slots as they can handle.

## Motivation / current pain

- **DSP is centralized** (`components/util/{overdrive,tremolo,flanger,fxdelay,
  reverb}` + `fxchain.h`), but the **rack around it is triplicated**: Keys,
  Synth, Tape each carry their own copy of the FX menu (`*_fx_items[]` + val/
  adj/action), the inlined chain in `process()`, and the autosave keys.
- FX menu is a flat 23-line list per machine (5 effects × toggle + params).
- CV matrix has **8 fixed destinations, none FX** (Keys:
  Cutoff/Reso/Env>Cut/Level/Pitch/Start/LoopMov/LoopLen). Arlo: FX params
  "should pretty much all be in the CV matrix also."

## The slot model

- **Rack = N slots, each = {effect kind, state, bypass}, run in order on the
  float buffer.** The `fxchain.h` unpack→stages→soft-clip runner we shipped is
  ALREADY the loop — replace the five hardcoded `if`s with
  `for slot: slot->process_f(slot->state, buf, n)`.
- **UI**: each FX# slot page selects the effect at the top row; the rows below
  are generated from that effect's param list (the one genuinely NEW mechanism:
  a **dynamic menu** whose rows change with the selection — verify menusys can
  rebuild rows at runtime; prototype this FIRST).
- **Routing**: serial 1>2>3 is free (that's the loop). A routing OPTION
  (parallel/send) needs extra buffers + mixing — defer to v2.

## What each effect needs (the descriptor / vtable)

Wrap each bespoke effect struct in one static descriptor entry:

```
name; init(state)/free(state); process_f(state, float *buf, int n);
params[]: { label, get()->float, set(float), format(), cv_scale };
preset_save(state)/preset_load(state);
```

Slot = `{ kind_id, void *state, bool bypass }`. The `*_block_f` float workers
already exist and are the `process_f`. `*_block_i32` wrappers stay for the
single-FX à-la-carte callers (Drums delay, Slicer reverb).

## Effect bricks (the palette a slot can hold)

Current 5: overdrive, tremolo, flanger, delay, reverb. Candidate additions:

- **Filter brick(s)** — a standalone multimode filter as an INSERT slot (place a
  filter anywhere: filter>delay>reverb). DSP already centralized in
  `components/util/svf` (Chamberlin, shared by deck/looper/synth/drums); Drums'
  master "DJ sweep" filter box is already exactly this. Two flavors wanted:
  - standard **cutoff + resonance** multimode (LP/HP/BP), optional LFO/env-follow.
  - **base/width** band filter (Arlo, LATER): center frequency ("base") +
    bandwidth ("width") controls instead of cutoff+reso — a band you position and
    widen. Bandpass/notch family.
  Especially useful for the **input-only FX machine** (no voice → a filter slot
  is how you filter incoming audio).

NOT in scope: the **voice filter** in Synth/Keys stays part of the VOICE (it's
env-modulated — `Env>Cut` — and sits before the rack; it defines the subtractive
instrument). The rack offers filter bricks as inserts; it does NOT absorb the
voice filter.

## Three ceilings on "how many slots" (untangle before baking numbers)

1. **Headroom/clipping** — WAS the limit ("Synth tops at 2"), **just fixed**
   (e6cf6ba). RE-TEST whether Synth does 3 now before hardcoding 2.
2. **CPU (`aus`, 1450 µs budget)** — the real hard ceiling, CONTENT-dependent
   (reverb pricey, tremolo ~free). Better than a fixed count: use the per-slot
   `cost_us` meters + a soft guard.
3. **PSRAM** — reverb tank ~170 KB EACH; delay/flanger have buffers. 3 slots
   each able to be reverb = ~510 KB. So slots must **lazy-allocate on effect
   selection**; maybe cap "one reverb-class slot" or a dedicated final reverb
   slot.

Rec: machines declare a MAX slot count; real limit driven by cost meter.

## CV matrix falls out for free

Once slots expose `params[]`, matrix destinations stop being hardcoded and
BECOME the slots' params (`Slot1.Drive`, `Slot2.Mix`…). The FX menu and the CV
matrix collapse to one generated source of truth.

## Input-only FX machine ≈ rack with no source

A new "FX" machine = read `in` (line input) → `fxrack_process_f` → `out`. Glitch
already proves live-input works. Falls out ~free once the rack is standalone;
good showcase/proof of centralization. (Tape's input processing is the same idea,
pure version.)

## Where it lives

New `components/fxrack/`: descriptor table, slot state, rack process
(float-through + soft-clip), dynamic menu builder, preset save/load. Machines
embed an `fxrack_t{ n_slots }` and call `fxrack_process_f(&rack, buf, n)` instead
of the inlined chain. The FX page becomes ONE shared page driven by the rack,
not 3 copies. CV matrix reads destinations from the rack.

## Open decisions (need Arlo)

1. **Slot flexibility**: any-of-5-in-any-slot (cleanest, reverb×N memory) vs.
   curated (slots 1-2 = mod/drive/delay, dedicated final reverb slot)?
2. **Slot count**: fixed per machine vs. cost-guarded "add until budget"?
   (+ re-test Synth=3 now that clipping's fixed.)
3. Migration of existing per-machine autosave FX keys (rvmx/dlymx/flgmx…) →
   slot format (migrate vs. reset).

## Staged plan

1. **Spike (Keys only)**: one `fxrack_t`, 3 slots, effect-select + dynamic
   param rows, serial routing, lazy-alloc. Prove the dynamic menu + the
   memory/CPU story on ONE machine. NO CV matrix, NO other machines yet.
2. Roll rack out to Synth + Tape; delete the triplicated FX menus/chains.
3. Rewire CV matrix destinations to the slots' params.
4. Add the input-only "FX" machine.
5. (v2) Routing options beyond serial.
